**4. Artifact Design and Scoring Specification**

**4.1 Artifact Overview**

The artifact consists of three components: an externalized control repository (Section 4.2), a scoring specification (Sections 4.3 to 4.5) and a research prototype that implements them (Section 4.6). This paper specifies and evaluates the deterministic scoring core only. The core contains no LLM component. An LLM-based semantic mapping layer is declared as the next stage of the work, and any such layer would supply answers that are confirmed by a human reviewer and then processed by the same scoring rules.

The workflow has four steps. The assessor declares the scope of the assessed system, including whether it processes personal data. The assessor then answers a predefined questionnaire with one question per applicable indicator. The scoring engine computes risk, weighted coverage, the worst-case upper bound and the Evidence Confidence Index (ECI) for each domain and each assessment scope. The report presents these results separately, together with a ranked list of indicators.

**4.2 Control Repository**

The repository is an externalized JSON file. It contains 35 indicators, of which 23 belong to the security scope and 12 to the personal-data scope, organized in seven domains (Table A1 in Appendix A). The indicators are drawn from NIST CSF 2.0 [2], CSA CCM v4.1 including its Cryptography, Encryption and Key Management (CEK) domain [3], GDPR Articles 5, 25, 32 and 35 [4] and the NIST Privacy Framework [5]. Each indicator is stored with the fields listed below.

- Identifier, indicator statement and the questionnaire question. The answer options of every question follow the standard set in Table 5, and Appendix A gives the indicator-specific meaning of the two end options (gap scores 0 and 4).
- Assessment scope, either security or personal data, and one assessment domain. Each domain belongs to exactly one scope, so that security and personal-data results cannot be mixed within a domain.
- Source references, giving the framework, the item identifier and the version of every source item the indicator draws on.
- A relationship term and note for each individual source reference, recorded explicitly in the spirit of the mapping approach of NIST IR 8477 [11].
- Applicability condition.
- Impact weight from 1 to 5 and a one-line rationale for the weight.
- Evidence guidance, describing what supporting evidence would be relevant to the indicator.

The indicators are selected and mapped by the following rules.

1. Candidate items are identified in the four sources if they can be assessed from questionnaire answers about a cloud-based SME system. Items that would require automated evidence collection or live scanning are excluded.
2. Each candidate is classified as security scope or personal-data scope.
3. Overlapping candidates are merged into a single indicator that keeps all of its source references.
4. Each indicator is assigned to exactly one domain, and each domain is assigned to exactly one scope. The number of domains is kept small so that each domain contains enough indicators for its results to be interpretable.
5. Where a security indicator also supports a GDPR provision, such as Article 32, the provision is recorded as an additional source reference and the indicator stays in the security scope.
6. GDPR-derived indicators that concern the processing of personal data as such, for example the principles of Article 5, data protection by design in Article 25 and impact assessment in Article 35, belong to the personal-data scope.
7. Every indicator must have at least one source reference, a question, a domain, an impact weight with a rationale and an applicability condition.

The selected indicators and their source items are listed in Appendix A. The selection of indicators from the CEK domain follows the same rules, and it is not taken to establish complete cryptographic coverage. GDPR provisions outside Articles 5, 25, 32 and 35, such as those on lawful bases, processors, the rights of individuals and breach notification, are not covered by the selected indicators, so the personal-data indicators assess readiness for the selected provisions only. The repository records the version of each source framework so that later updates can be traced.

**4.3 Scoring Specification**

*Questionnaire answers and indicator values.* Each indicator k has an impact weight I_k, an integer from 1 to 5. Every question offers the same seven answer options, which Table 5 maps to a gap score G_k, an integer from 0 to 4, or to a status. A gap score of 0 means fully implemented and 4 means not implemented. An indicator has one of three statuses. It is assessed if one of the five implementation options is selected, which records a gap score. It is unassessed if the question is unanswered or answered as unknown. It is not applicable if the assessor selects the not-applicable option, and this option requires a written justification. The engine does not accept it without one. Unknown and not applicable are separate options, so an unknown answer is never silently treated as not applicable.

Table 5. Answer options and their mapping to gap scores and indicator status.

| Answer option | Resulting status | Gap score |
| --- | --- | --- |
| Fully implemented | Assessed | 0 |
| Mostly implemented, with minor gaps | Assessed | 1 |
| Partially implemented | Assessed | 2 |
| Implemented only to a minimal extent | Assessed | 3 |
| Not implemented | Assessed | 4 |
| Unknown or not answered | Unassessed | None |
| Not applicable, with written justification | Not applicable | None |

*Impact weights.* The impact weights are researcher-defined and follow the rubric in Table 6. The researcher judges each indicator against three criteria: the consequence of a failure of the control for confidentiality, integrity, availability or personal data protection; the breadth of the assets or processes affected; and the extent to which other controls depend on it. The levels of Table 6 guide an overall judgement and are not rigid mathematical thresholds. Where an indicator could fit two adjacent levels, the researcher assigns the weight from an overall judgement against the three criteria, and the rationale stored in the repository records the reason. The weights are fixed before the scenarios are run and are not adjusted to the results. They are not derived from incident data or expert elicitation. Their influence is examined through sensitivity analysis (Section 5).

Table 6. Impact weight rubric.

| Weight | Description |
| --- | --- |
| 5 | A failure could affect the whole assessed system or all of its protected data, or many other controls depend on the indicator |
| 4 | A failure could seriously affect a critical asset, data store or service |
| 3 | A failure could cause a significant but contained impact on one component, data set or process |
| 2 | A failure would have limited impact or mainly weakens another control |
| 1 | A failure would have minor impact, and the indicator mainly supports good practice or documentation |

*Sets.* Let g denote a group of indicators, which is either a domain or an assessment scope. Let P_g be the applicable indicators of g, that is, the indicators in active scopes that are not declared not applicable. Let A_g be the assessed indicators of g, so that A_g is a subset of P_g. Let U_g be the unassessed indicators, so that U_g equals P_g without A_g.

*Observed risk.* The observed risk of group g is computed over assessed indicators only:

R_g = 100 × Σ(I_k × G_k) / (4 × Σ I_k), with both sums over k in A_g.

This is equivalent to R_g = 25 × Σ(I_k × G_k) / Σ I_k. It ranges from 0, when every assessed indicator has a gap score of 0, to 100, when every assessed indicator has a gap score of 4. If A_g is empty, R_g is undefined, and the report shows the group as not assessed and gives no risk value.

*Weighted coverage.* The weighted coverage of group g is the share of applicable weight that has been assessed:

C_g = 100 × Σ I_k over k in A_g / Σ I_k over k in P_g.

It is undefined if P_g is empty. If P_g is not empty and A_g is empty, C_g is 0.

*Worst-case upper bound.* The worst-case upper bound applies the same formula with every unassessed applicable indicator set to a gap score of 4:

R_g(ub) = 100 × (Σ(I_k × G_k) over k in A_g + 4 × Σ I_k over k in U_g) / (4 × Σ I_k over k in P_g).

It is undefined if P_g is empty. If P_g is not empty and A_g is empty, the bound is 100. If A_g is not empty, the bound equals R_g × C_g / 100 + (100 - C_g). The bound is reported as a sensitivity bound only. It is not an estimate of the actual risk.

*Evidence Confidence Index.* The ECI is defined for each assessed indicator from four dimensions: verification, completeness, relevance and recency. Each dimension is rated by the assessor from 0 to 3 according to the anchors in Table 7, using the documented evidence. The ratings are not inferred by the software. In this study a single assessor assigns the ratings, so no procedure for disagreement between reviewers is needed. Let e_V, e_C, e_R and e_T be the ratings for verification, completeness, relevance and recency. If no evidence information is provided for an assessed answer, all four ratings are 0, which lowers the ECI and never changes the gap score. The dimension weights are fixed a priori as the integers 2 for verification and 1 for each of the other three dimensions, which correspond to the proportions 0.4, 0.2, 0.2 and 0.2. Verification receives the largest weight because it separates a statement that is merely asserted from one that is supported by an artifact. With the integer score s_k = 2 × e_V + e_C + e_R + e_T, the indicator-level ECI is

E_k = 100 × s_k / 15.

The ECI of a group is the impact-weighted mean of the indicator-level ECI over its assessed indicators:

ECI_g = 100 × Σ(I_k × s_k) / (15 × Σ I_k), with both sums over k in A_g.

It is undefined if A_g is empty, so that its denominator is never zero. The alternative with equal dimension weights that is examined in the sensitivity analysis uses s_k = e_V + e_C + e_R + e_T and the denominator 12 instead of 15. The ECI describes the evidence supporting the answers. It does not measure whether a control is effective.

Table 7. ECI rating anchors.

| Dimension | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| Verification | Unsupported statement | Self-reported with a stated basis | Supporting artifact referenced | Supporting artifact reviewed by someone other than the respondent |
| Completeness | No evidence | Covers a small part of the indicator scope | Covers most of the scope | Covers the full scope |
| Relevance | Unrelated to the indicator | Indirectly related | Related | Directly addresses the requirement |
| Recency | Date of the evidence unknown | Evidence dated more than 24 months before the assessment | Evidence dated more than 12 months and up to and including 24 months before the assessment | Evidence dated up to and including 12 months before the assessment |

The recency date is the date of the evidence artifact, for example a policy review, a configuration export, a report or a log, measured from the date of the assessment. The thresholds of 12 and 24 months are researcher-defined and fixed a priori.

*Undefined cases.* Table 8 summarizes how each output is reported when a group has no applicable or no assessed indicators. An undefined value is never displayed as zero.

Table 8. Reporting of undefined cases.

| Situation | Risk | Weighted coverage | Upper bound | ECI |
| --- | --- | --- | --- | --- |
| P_g is empty (all indicators not applicable) | Not applicable | Not applicable | Not applicable | Not applicable |
| P_g is not empty and A_g is empty | Not assessed | 0 | 100 | Not assessed |
| A_g is not empty | Computed | Computed | Computed | Computed |
| Personal-data scope is undetermined (Section 4.4) | Undetermined | Undetermined | Undetermined | Undetermined |

The last row applies to the personal-data scope and its domains only. The security scope and its domains are calculated according to the other rows regardless of the personal-data declaration.

*Indicator ranking.* Assessed indicators are ranked by the priority score p_k = I_k × G_k in descending order. Ties are broken by ascending indicator identifier, so that the ranking is deterministic.

*Illustrative example.* The following hypothetical numbers explain the formulas and are not results. A domain has four applicable indicators. Indicator a has I = 5 and G = 2, indicator b has I = 3 and G = 0, indicator c has I = 4 and G = 4, and indicator d has I = 2 and is unassessed. The sum of I × G over the assessed indicators is 26 and the assessed weight is 12, so R = 25 × 26 / 12 = 54.2. The applicable weight is 14, so C = 100 × 12 / 14 = 85.7. The upper bound is 100 × (26 + 4 × 2) / (4 × 14) = 60.7. For one assessed indicator rated 3, 2, 3 and 1 on verification, completeness, relevance and recency, s = 2 × 3 + 2 + 3 + 1 = 12 and E = 100 × 12 / 15 = 80.0.

**4.4 Conditional Personal-Data Module**

The assessor declares whether the assessed system processes personal data, and the declaration has three states.

- Yes: the personal-data scope is active, and its indicators are applicable unless an indicator has an additional applicability condition of its own. PG-05 applies where the processing is likely to result in a high risk to individuals. It may be declared not applicable only on the basis of a documented screening, and it remains unassessed if screening has not been performed or its outcome is unknown (Appendix A, Table A3). Activating the module therefore does not by itself activate every individual indicator.
- No: the personal-data scope is inactive. Its indicators are reported as not applicable with the justification that no personal data processing was declared.
- Undetermined: the applicability of the personal-data scope is unknown. Its indicators are excluded from all calculations and are not treated as inactive. The report shows the scope as undetermined, gives no risk, coverage, upper bound or ECI for it, and states that privacy readiness cannot be assessed until the declaration is made. The security results are still calculated and reported in full.

Risk, coverage, upper bound and ECI are computed separately for the security scope and the personal-data scope, and for each domain within them. Because every indicator belongs to exactly one scope, every domain belongs to exactly one scope and each formula uses only the indicators of its own group, the security results are independent of the state of the personal-data module. The paired test in Section 5 checks that the implementation preserves this property. The personal-data indicators are readiness indicators. Their results are not a statement of GDPR compliance. The separation of the two scopes is an assessment-design decision, and it does not imply that security and privacy risks are independent in real environments.

**4.5 Interpretation Rules and Reporting**

The following rules apply to every report.

1. Unassessed indicators are never treated as zero risk.
2. Not-applicable indicators are excluded from the applicable set and carry a written justification.
3. Every risk value is shown together with weighted coverage, the numbers of assessed and applicable indicators and the upper bound, so that a score based on a small share of a domain is visible as such.
4. A group with no assessed indicator is reported as not assessed and has no risk value. A group with no applicable indicator is reported as not applicable. A personal-data scope with an undetermined declaration is reported as undetermined, and the security results are reported regardless (Table 8).
5. Risk, weighted coverage and ECI are always reported separately and are never merged into a composite score.
6. Report wording is cautious and uses terms such as "supports" and "readiness indicators". The report makes no claim of legal compliance and states that its output is decision support that requires human review.

**4.6 Research Prototype and Verification Support**

The prototype is implemented with Django and SQLite and provides an input form, a result page and a report. The scoring engine is a separate module without dependencies on the web framework or the database. It computes all sums as integers and performs one division for each reported metric, namely risk, weighted coverage, the upper bound, and the indicator-level and group-level ECI. It rounds values to one decimal place for display only. The indicator ranking uses integer products only. The engine uses no randomness and makes no external calls, so identical input produces identical output.

Automated tests verify that the implementation conforms to the specification. They cover the cases in which the specification could fail: repeated runs of identical input give identical output, an empty assessed set, full coverage and all indicators unassessed. Further tests check the empty applicable set and the undetermined personal-data state against Table 8, the relation between R, C and the upper bound given in Section 4.3, the mapping of answer options in Table 5, the rejection of a not-applicable status without a justification, the additional applicability condition of PG-05, the ECI result for all 16 combinations of the end values 0 and 3 of the four ratings, and the independence of the security results from the state of the personal-data module. The rule that an unknown PG-05 screening outcome leaves the indicator unassessed is tested as well. The source code and the repository are to be made publicly available with a README.
